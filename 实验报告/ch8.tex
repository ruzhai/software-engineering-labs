\subsection{这次设计真正做成的事}

如果只留三句话，本设计做到的是：

\textbf{一、把「不超卖」从一句要求变成了一行 SQL。} 需求里写的是「同一房型同一晚最后一份库存，100 个并发请求只能成功 1 个」；设计里它变成 \texttt{UPDATE ... WHERE sold + n <= online\_limit} 这一句，以及 5.3 节那张时序图上两条相邻的 UPDATE 之间隔着 MySQL 行锁。这句话之所以重要，是因为它把一条无法验证的要求变成了一个可以写测试用例的东西。

\textbf{二、把「状态一致」从一句话变成了两张转换表。} 订单六态与房间六态各自穷举了允许的边与禁止的边，非法转换统一抛异常。相比「保证状态正确」这种表述，一张列了 9 条允许边与 12 条禁止边的表，在实验三是可以照着写 switch 的。

\textbf{三、把「界面」从装饰变成了约束的证据。} 16 屏里最关键的几屏不是在展示好看，而是在证明某条规则确实存在：11 屏的线下保留额度表证明了 REQ-033 的公式在算；09 屏的三步流程条证明了 REQ-018 没有被做成五步；16 屏那条「与首次退款同一幂等键」的审计记录证明了 REQ-009 只退一次。\textbf{如果某一屏删掉后，没有任何一条需求失去落点，那这一屏就是多余的}——本设计 16 屏没有这种屏。

\subsection{设计的薄弱之处}

以下几处是本设计自己知道没做扎实的地方，写在这里而不是等别人问：

\begin{enumerate}[leftmargin=3.2em]
  \item \textbf{REQ-035、REQ-036 没有覆盖。} 订单排房时限与账号注册登录在实验一即标为「待确认」，本设计据此不覆盖。这是一个可以说得过去的处理，但也意味着\textbf{如果实验三开始前这两条被确认，模块划分需要重新过一遍}——注册登录会落到 M1，排房时限会同时牵动 M5 的定时任务与 M7 的排房逻辑。

  \item \textbf{改期（REQ-031）的边界只画到主流程。} 现有设计说清了「按新价重算快照、差额调库存」，但没有细化两个边界：改期后新房型当日库存不足时，是整单失败还是允许部分改期；同一订单已经产生过一次差额退款后再改期，幂等键的「第几次退款动作」如何计数。第 4 章把幂等键设计成「订单号 + 取消动作序号」正是为了能容纳这种情况，但具体序号怎么分配没有写死。

  \item \textbf{缓存一致性只在改价场景讨论过。} 3.5 决策七给了改价后主动失效的做法，但房型上下架、维修登记这两类会改变可售量的操作，哪个该失效缓存、失效到什么粒度，没有专门讨论。按现有设计它们都走「写库即失效」，代价是缓存命中率下降，这一点没有量化。

  \item \textbf{退款失败的兜底只到「进人工队列」。} 5.6 节的时序图说退款再失败就进人工队列并告警，但没有定义队列的保留时长、超时升级规则、以及人工处理失败后的最终状态。这是本设计在「异常路径」上唯一没有闭环的地方。

  \item \textbf{UI 只画了正常态与关键异常态。} 16 屏覆盖了空态（02 屏的筛选无结果未画）、满房态（03 屏的重置灰）、超限态（11 屏的告警），但\textbf{支付失败页、网络异常页、权限不足页没有出图}。这些页面在实现时必须补，只是它们不承载业务规则，因此本设计优先保证了有规则的那部分。

  \item \textbf{界面未做无障碍与对比度校验。} 状态色用了红 / 橙 / 蓝 / 绿四组，其中「需打扫」的橙与「维修中」的红在色弱情况下区分度不足，实际实现应补充图标或纹理差异。本设计依赖的是文字标签兜底（每格都写了状态文字），但这只是补救，不是无障碍设计。

  \item \textbf{接口只到模块边界，没有到方法级。} 报告里说清了「M5 调 M4 释放库存」「M6 发布支付成功事件」，但没有给出方法签名与 DTO 结构。这是刻意的取舍——在没有确定技术栈的情况下先写签名，很可能在实验三被推翻；代价是实验三开始时要先把这一层补上。
\end{enumerate}

\subsection{对实验三的衔接}

本设计可以在实验三直接用的东西有三样：表结构（第 4 章，17 张表的字段与约束）、状态转换表（5.4 节，可直接写成枚举与 switch）、界面（第 6 章，16 屏可作为前端页面骨架）。需要先补的也有三样：接口签名、缓存失效的完整清单、异常路径的收尾规则。

实现顺序上，建议按依赖倒序：先落地 M2 门店与房源（其他模块都要读房间与房型）、再做 M3 定价与 M4 库存（这两块决定了下单能否成立）、然后 M5 下单与 M6 支付回调（这是全系统唯一有并发正确性要求的两段，应当最早写测试）、接着 M7 房态与 M10 通知、最后 M8 评价与 M9 审计。M1 账号与权限从第一天就要有最小可用版本，因为它决定了其他模块的接口需不需要额外参数。

最后一点体会：这次实验最耗时的部分不是画图，而是\textbf{发现两处设计互相矛盾}。库存算出的可订量与界面上的「剩 3 间」矛盾、片区营收的环比与六店相加矛盾、取消规则的界面文案与 REQ-021 矛盾——每一次都是先把「哪一处是权威的」定下来，再改另一处。这件事无法通过更仔细地画图来避免，只能靠\textbf{先写下基准、再让所有产物对着基准}来做。如果这个实验只留一条经验，就是这一条。
