# 实验三 AI 使用记录

记录实验三实现过程中实际让大模型做了什么、哪些地方不符合预期、怎么处理的。
按发生顺序写，不补造。

## 一、需求对齐与技术选型

**让模型做的**：读实验三要求 PDF 与实验二的 `design.md`、UML 类图，列出实现前需要定下来的决策。

**结果**：模型给出语言、模块覆盖、界面形态、持久化、并发、代码分包、测试接缝等一组问题，逐个确认后写进 `spec.md`。

**不符合预期之处**：模型最初推荐 Java，理由是类型映射贴近 UML、Checkstyle 是课程点名工具。实测本机只有 JRE 1.8，没有 `javac`、Maven、Gradle，装 JDK 又占 C 盘。改回 Python 后重新确认了构建方式。

## 二、仓库整理

**让模型做的**：把实验一、实验二两个独立仓库合并成一个课程级仓库，并保留原有提交历史。

**结果**：外层的实验一、实验二 `.git` 会造成嵌套仓库（外层只能记下 gitlink，推上去是空目录），模型用 `git subtree` 把两边历史并入 `lab1/`、`lab2/`。

**不符合预期之处**：远程仓库 `software-engineering-labs` 已经存在且是公开的，里面有更完整的需求规格。本地仓库克隆出来的 `requirements.md` 只有 31 条需求，因为最后 5 条一直留在工作区没有提交。模型一开始按本地版本合并，对比后才发现远程版才是终稿，改用远程历史做底座。这件事说明「本地仓库里的文件」和「远程仓库里的文件」不一定一致，不能默认本地更新。

## 三、实现阶段

**让模型做的**：按 M1–M10 逐模块生成 model / repository / service 与测试。

**有效的地方**：状态机允许表、库存条件扣减、可售上限公式这类规则明确的代码，一次生成基本可用；测试用例与需求编号能对上，改起来有准绳。

**不符合预期、需要返工的地方**：

1. **登录失败计数不落库。** 模型把「失败次数 +1」和「抛出校验错误」写在同一个事务里，抛异常触发回滚，计数永远是 0，账号锁定形同虚设。测试 `test_wrong_password_locks_account_then_unlocks` 暴露后，改为先把修改提交、再在事务外抛错。
2. **操作日志没有门店归属。** 日志表只有操作人，店员给顾客办的事记在顾客名下，店长按门店查日志查不到任何东西。给 `audit_log` 加了 `store_id`，写入时按对象反查门店。
3. **价格锁的持有范围错了。** 模型最初把锁放在数据库事务内部，出事务即释放，但写事务还没提交，下单方可能拿到锁读到旧价——正是 REQ-012 要求避免的情况。改成事务之前加锁、提交之后释放，并统一「先价格锁后写事务」的顺序避免死锁。
4. **种子脚本用 id 后缀猜房型名。** 为了少写一个查询，模型用 `room_type_id.endswith("0")` 判断是不是大床房，结果双床房也被设成大床房的价格。改成按房型名取值。
5. **并发测试里锁超时被当成普通拒绝。** 100 线程抢房时，部分线程其实是等锁超时而非库存不足，测试仍会通过，掩盖了问题。改成把数据库层异常单独记录，并放宽测试里的锁等待时间。

## 四、代码风格

**让模型做的**：用 black 格式化、pylint 检查。

**结果**：pylint 从 9.7 调到 10.0。调整的大头是阈值配置（参数个数、实例属性数、模块行数）以及为 UI 类关掉继承层数检查；真正因为代码问题改掉的是未使用变量、重复的分支判断、`bar` 这类无意义命名。

## 五、独立评审轮次

实现完成后另开一个对话做独立评审：按实验要求打分、找缺陷、修。评审 agent 两次中断（一次长时间无进展、一次连接被重置），中间结论只留下「确认 6 个缺陷」，没有具体清单，于是改为自己按同样的思路复核。

写探测脚本逐条验证，确认并修掉的问题：

1. **同一订单可以建多笔支付。** 第二笔回调到达时订单已是已确认，代码直接标记支付成功，既不拒绝也不记对账——顾客被扣两次钱且系统里查不到异常。改为建单时拒绝重复支付；回调侧若发现同一订单有两笔成功支付，记一条 `DUPLICATE_PAYMENT` 对账差异。
2. **账号停用后，已登录的会话仍然有效。** 服务只信 Session 里的角色和门店快照，从不回查账号状态。新增 `core/auth.ensure_active`，在下单、取消、支付、入住、退房、房态、改价、评价、删除审批等入口的事务里查一次。
3. **片区负责人能查前台个人明细。** 违反 REQ-026。改为只返回各店店长，并校验门店属于本片区。
4. **前台开单没有实现。** REQ-033 要求前台开单从线下保留额度扣减，代码里有 `reserve_offline` 但没人调用。补 `create_walk_in_order`，并加测试确认线下已售增加、线上库存不变。
5. **未到店订单无法取消。** REQ-022 说未到店期间顾客取消按 REQ-021 处理，但取消接口把状态限定在待支付与已确认。放开未到店，并按 REQ-021 不产生退款。
6. **多间订单在界面上无法入住。** 入住按钮只分配一间房，两间的订单会报「请先排房」却没有排第二间的入口。改为按订单需求量一次分配足额房间。

## 六、界面实际使用轮次

按真实使用顺序把系统走了一遍并逐步截图，又发现一批只有真正跑起来才看得到的问题：

1. **所有界面的内容区都是空白的。** `Screen` 基类建了 Frame 却从没 `pack` 进主窗口，控件全都建在 1×1 的不可见容器里。之前的自动化冒烟只调用方法、检查返回值，没有检查渲染，因此完全没发现。修复后给走查脚本加了断言：每个界面必须 `winfo_ismapped()` 且宽度大于 200，否则直接失败。
2. **截图区域错位。** 系统缩放 150%，Tk 用逻辑像素、截图用物理像素，按 1.5 倍换算才能截准。
3. **查询结果缺「剩余数量」。** REQ-002 要求展示剩余可售，原来只显示房间总数，补了可售列。
4. **订单列表显示门店 id 后 6 位和英文状态。** 改成门店名与中文状态。
5. **操作日志里写的是房间 id 和支付单号。** 改成房号和订单号。
6. **审批中心没有可审的数据。** 走查时补造了改价申请与取消申请，截图才反映真实待办状态。

## 七、按实验二设计重做界面

第一版界面是默认风格的表格堆叠，与实验二的桌面端差距明显。参照实验二的布局重做：

- 抽出 `ui/theme.py` 统一配色（浅灰底、白卡片、蓝色主色、状态色）、字号与控件样式
- 外壳改为「左侧导航 + 顶部标题 + 内容区」，导航按角色生成并高亮当前页
- 每个页面用「卡片 + KPI 卡片 + 数据表 + 操作栏」组织，表格行高、表头、选中态统一样式
- 查询页补「热门房型」，片区概览补顶部指标，房态看板补五类状态的统计卡片

重做后又修掉的问题：表格固定行高把操作栏挤出可视区（统一压到 8 行）、申请人显示成用户 id 后缀（改为姓名）、房型详情与注册弹窗的样式不统一（统一用 theme 里的卡片与按钮）。

## 八、边界与运行时检查

又写了两支探测脚本：一支在空库（只有账号和门店、没有任何房型房间）下把四类角色的全部界面点一遍，并逐个触发十八个动作按钮；一支造出真实数据后点击审批、停用、打扫、开单等操作。

覆盖到的边界：18:00 整点取消、支付超时正好 15 分钟与 15 分 01 秒、21:59 与 22:00 的未到店判定、次日 11:59 与 12:00 的逾期释放、价格区间上下限端点、空请求号、间数为 0、离店早于入住、入住日期在过去、不存在房型、超出已设价区间；并发侧跑了三轮 40 线程抢 2 间房，核对成功数与已售数都等于 2。

发现并修复：

1. **片区负责人停用店长会失败。** 店长账号只绑了门店、`area_id` 为空，权限判断直接比 `target.area_id` 永远不相等。改为通过门店反查片区。
2. **查询人数填非数字时弹出 Python 异常文本。** `int("")` 抛 `ValueError`，被兜底捕获后原样显示。改为转成字段级校验提示。

## 六、体会

- 规则型代码（状态机、库存、时间边界）大模型生成质量高，但**事务边界**和**锁的作用域**这类看不见的约束最容易错，必须靠测试兜底。
- 需求编号写进测试名和注释里，返工时能快速判断动一处会不会碰到别的需求。
- 大模型倾向于把注释写成「这行在做什么」，而不是「为什么这么写」；关键决策处的注释需要人工重写。
